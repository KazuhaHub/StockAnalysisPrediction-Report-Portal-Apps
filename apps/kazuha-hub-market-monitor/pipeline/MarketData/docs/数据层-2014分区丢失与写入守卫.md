# 数据层事故复盘：2014 分区被增量写整块顶掉

**时间**：2026-11-08 09:18 发生，11:20 发现，11:40 修复完毕；12:10 补上写前快照与每日体检
**影响面**：968 只票的 2014-06-03 ~ 2014-12-31 共 **138,975 根日线**从本地库消失
**是否影响已发布的判定**：否（检验起点 2018，取数从 `>= 2018` 的年分区开始，2014 分区不参与）
**是否影响 `doctor` 结论**：是当时没有一条检查能发现它——这才是最该修的地方

---

## 1. 怎么发现的

收尾核对工作日志时顺手跑了一次 `md.verify()`，报「meta 对不上的票 **1201**」，
样例清一色是 `声称 3023 / 实际 2877`——差 146 根，正好是 2014-06-03 到 2014-12-31
的交易日数。再按分区数一遍：`2014.parquet` 只剩 1,429 只票，而且其中 1,428 只是
当天新扩进来的，原库的 968 只一只不剩。

同一时刻 `doctor` 的结论是「0 错误 / 5 警告 / 12 通过」。
两边不矛盾：`doctor` 的 11 项全在问「池子里有什么」（规模、覆盖、能力表、漂移、
幸存者偏差），没有一项在问「库里声称的，和磁盘上真有的，对得上吗」。

## 2. 根因

`market_data._new_partitions()` 里这一段：

```python
if os.path.exists(p):          # 分区存在 → 读旧数据、合并、去重
    old = pd.read_parquet(p)
    merged = concat([old, chunk]).drop_duplicates(...)
else:                          # 分区不存在 → 只把本批数据写回去
    merged = chunk.drop_duplicates(...)
```

分区文件在写入那一刻不存在时，走 else 分支，**一批增量被当成整年数据写回去**。
写入是 `os.replace(tmp, p)` 原子替换，旧行没有第二份，也不报错。
09:18 那次 `add 301511 300274`（2 只，成功 1 只）之后 `2014.parquet` 就只剩这两只的量，
09:31 扩池 ingest 再往上叠 1,428 只新票，事故彻底成型。

还有一个附带产物：`2014.parquet` 里多了一行 `000001 2026-11-06`，
`open/high/low` 全 NaN、`close=1.0`。它和 `2026.parquet` 里那根真 bar 撞成
`(code,date)` 重复，并且会在 000001 的序列尾造一个 −99.8% 的假收益。
来源是 `ingest()` 用 `b.get("o", np.nan)` 取价——缺字段不报错，直接写 NaN。

## 3. 修了什么

### 3.1 两道写入守卫（`market_data.py`）

| 守卫 | 触发条件 | 为什么这么设 |
|---|---|---|
| 只增不减 | 合并后行数少于旧数据，或票数少于旧数据 | 写入是原子替换，丢掉的旧行不可恢复；"少一行"就中止，不留解释空间 |
| 分区不许凭空消失 | 分区文件不存在，且该年份落在 meta `date_range` 内 | 库声明区间内的每一年都必须有 parquet。只有"往更早年份扩历史"和"新年度第一天"允许新建 |

配套 `rebuild_partition(year, df)` 作为唯一的显式缩减入口——真要重写一整年，
写清楚，而不是把守卫关掉。空表直接拒绝，不许把分区清空。

### 3.2 毒 bar 挡在门口（`ingest()`）

四价必须齐全且 `close > 0`，否则丢弃并打印条数。缺价的 bar 不是"便宜的数据"：
它在序列里就是一个 −99% 的单日收益，而 `verify` 只查重复和 OHLC 关系，
`NaN` 全过。

### 3.3 `doctor` 加「库对账」（`qdata.data_integrity` + `qsr doctor`）

对一次「meta 声明的每票行数」与「磁盘真实行数」，两个方向分开报：

- `meta > disk` → **error**，写的是"历史被写没了，先修数据再引用任何判定"；
- `meta < disk` → warn，只是增量/扩池后没 `rebuild_meta`。

分开数的原因：混成一个净差额会互相抵消。这次就是 968 只少 138,975 根、
233 只多 355,728 根，净值还是"多"，一眼看不出危险方向。

只读 `code` 列，13 个分区约 2 秒；不进 `load_universe`，`test --all` 连跑 18 次
不会为此多付任何时间。

### 3.4 数据修复（`repair_2014.py`）

两阶段，和扩池同一套纪律：`--stage pull` 只新建 `pull_cache/rep_*.parquet`（可后台），
`--stage ingest` 才碰 `bars/`（需前台审批，因为要 `os.replace`）。

- 目标 968 只，窗口 2014-06-03 ~ 2014-12-31；
- 实际拉回 **138,976 行 / 968 只**，与丢失量 138,975 差 1 根（某只票当年多一个交易日）；
- 四轮补齐（429 限流）：691 → +240 → +35 → +2，总耗时约 34 分钟；
- 落盘后 `rebuild_meta()`，`n_bars` 全库重算。

结果：`2014.parquet` 从 201,828 行 / 1,429 只 → **340,803 行 / 2,396 只**（清理毒行后）。
全库 8,973,551 → **9,112,526 根**，350 MB。

## 5. 这次真正的教训

不是"加个 try/except"，而是**检查项的方向要覆盖「声明 vs 实际」**。
框架里原有的 11 项全部是"内容检查"：池子多大、覆盖多少、能力表填没填、
判定漂移没有。它们共享一个隐含前提——**磁盘上的东西就是全部历史**。
这个前提一旦被原子写破坏，所有基于它的检查继续全绿。

同类风险的清单（还开着）：

- `bars/` 没有任何版本或快照，一次原子写就是终局。每天 `update` 都在做写操作，
  单个分区跑坏的概率不为零。**建议**：`update` 前后各记一次
  `(分区, 行数, 票数)` 到 `updates.jsonl`，对不上就报警——成本几乎为零。
- 退市股 170 只缺 `sw1`（申万成分表只含现存标的），行业中性化时被略过。
- A 批 93 只仍卡 429（`pending_add.txt`），补完 `n_stocks` 会变、判定须重跑。

## 6. 第二轮：把"能回滚"和"每天自动发现"补上

上一条"建议"当天就落地了。数据质量的完整答案不是"报警"，是
**写之前留一份能退回去的副本，写之后每天自动比一次**。

### 6.1 三道防线

| 防线 | 做什么 | 成本 | 拦得住什么 |
|---|---|---|---|
| `partition_stats()` | 写前后各取指纹：行数 / 票数 / 日期区间 / 落错分区的行数 | 全库约 1 秒 | 事后发现，给出准确差额 |
| 硬链接快照 | 写前把**将要改动的分区**钉到 `snapshots/<时间戳>-<来源>/` | 微秒级，**额外占盘 0** | 可回滚 |
| 只增不减守卫 | 合并后行数或票数比旧数据少 → 拒绝写 | 0 | 不让它发生 |

三道全部收在 `_new_partitions()` 里，因为它是**唯一的分区写入口**：
`ingest`、扩池脚本（`expand_run.py`）、修复脚本（`repair_2014.py`）都走它。
第一版把快照挂在 `ingest` 上，结果扩池那条路绕开了 `ingest`——
最大的那次写入（1,449 只新票 / 13 个分区）恰好没有快照。现在
`test_new_partitions_is_the_choke_point` 钉住这一点。

`rebuild_partition()`（按定义就会删行的整分区替换）也照样先拍快照：
演练里被砍掉的 33 万行，就是靠它拿回来的。

硬链接能成立，靠的是写入方式本身：`_new_partitions` 是"写 `.tmp` 再 `os.replace`"，
替换只改目录项，**旧 inode 内容完好**，所以快照指向的仍是旧数据。
只有该分区真被替换之后，旧 inode 才由快照独占（日常 update 约 28 MB）。保留最近 10 份。

实测：13 个分区全量快照后 `du -sh ~/MarketData` 仍 **497 MB**（bars 350 + pull_cache 139 + meta 1），
再拍第二份 2026 也不变。单独 `du -sh snapshots` 会显示 350 MB，那是硬链接被重复计数
（`du` 只把一块 inode 算给先看到的那条路径）——**别拿这个数当"快照很贵"的证据**。

`ingest` 默认 `protect=True`；`import_ss_cache` 显式关掉（源 json 还在，
且一次迁移会触碰全部 13 个分区、连做几十批）。

### 6.2 `check`：0.9 秒的每日体检

`verify` 要把 900 万行读进内存（约 30 秒），当不了每天的第一道；
`check` 只读 `code`/`date` 两列做算术，全库 **0.9 秒**，查三件事：

1. 分区齐全——库声明区间内每年都必须有 parquet（2014 事故的形状）；
2. 分区纯度——每根 bar 必须落在文件名那一年
   （2014 分区里那根 000001 2026-11-06 的假 bar 就属于这类）；
3. 每票行数对账——`meta > disk` 报失败，`meta < disk` 只提示重算 meta。

`update.sh` 每个交易日 **23:30** 跑完 `update` 立刻跑 `check`，并且**退出码现在会传出去**——
以前 `{ ... } | tee` 让脚本永远返回 0，定时任务永远显示成功，出问题只能靠人翻日志。

### 6.3 端到端演练（真实库）

```
快照 20261108-120959-498-e2e（1 个分区 / 硬链接）
故意把 2026 分区砍掉一半 → 336,896 行 / 1,667 只
check：失败，报「少 336,897 根」
restore 该快照 → check：通过，全库 9,112,526 行
```

演练快照已清理，留了一份全库基线 `20261108-121009-279-baseline`（13 个分区，占盘 0 B）。

### 6.4 测试

`test_market_data.py` 19 → **35 条**，新增覆盖：硬链接同一 inode、
不存在年份跳过、只留最近 N 份、ingest 自动快照并把写前指纹写进
`updates.jsonl`、`_new_partitions` 是唯一写入口（直接调用也有快照）、
restore 先备份当前状态、restore 未知快照报错、`_diff_stats` 只报缩减、
分区纯度、`check` 的四种结论（通过 / 变少 / 缺分区 / 变多）。

### 6.5 仍然开着的口子

- **快照只保护"写路径"**：手动 `rm` 或第三方脚本动 `bars/` 时救不了，
  那种情况只能靠次日 `check` 事后发现。
- `snapshots/` 只留 10 份，第 11 次写入会删最旧那份；危险操作前先 `snapshot --tag 动手前`。
- 每日 `check` 不查 OHLC 与重复（那是 `verify` 的活），周度仍应跑一次 `verify`。
